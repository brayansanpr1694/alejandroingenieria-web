Tu equipo tiene Wi-Fi, pero la web no carga

DiagnósticoPaso 6 de la ruta de estudio· 6 min de lectura

Revisión técnica: 27 de noviembre de 2026.

El ícono del Wi-Fi dice “conectado”, pero la página no carga. En lugar de reiniciar todo al azar, puedes seguir un orden que separa el problema en partes: tu configuración, el DNS o la conexión al sitio. Es el mismo razonamiento por capas del modelo OSI.

1. Empieza por el alcance

Prueba otro sitio y otro dispositivo conectado a la misma red.

  • Si falla un solo sitio, anota su dirección y el error exacto del navegador.
  • Si fallan varios dispositivos, la causa probablemente está en algo que comparten: el router o la conexión del proveedor.

2. Revisa tu dirección y tu puerta de enlace

# Windows (PowerShell o CMD)
ipconfig /all

# Linux
ip addr
ip route

# macOS
ifconfig
route -n get default

Busca la interfaz Wi-Fi y anota sus direcciones, máscara o prefijo, puerta de enlace y servidores DNS. Si esperabas una IPv4 asignada por DHCP y solo ves una dirección 169.254.x.x, investiga la configuración automática: puede tratarse de una dirección IPv4 de enlace local. Es una pista, no una prueba concluyente de la causa ni del estado de IPv6.

Prueba ping a la puerta de enlace que aparece en tu configuración. Una respuesta aporta evidencia de conectividad IP con ella. Si no responde, revisa asociación Wi-Fi, configuración y políticas: el router puede filtrar ICMP aunque permita otro tráfico. Un ping fallido por sí solo no localiza la avería.

3. Separa DNS de la conexión HTTPS

Primero comprueba si puedes resolver el nombre. Luego, si el equipo puede abrir una conexión TCP al puerto 443:

# Consulta DNS (si nslookup está instalado)
nslookup example.com

# Windows PowerShell: conexión TCP
Test-NetConnection example.com -Port 443

# Linux / macOS: conexión TCP, si nc está instalado
nc -vz example.com 443
  • Si DNS falla: anota el error y, en una red donde esté permitido, compara con nslookup example.com 1.1.1.1. Una diferencia es una pista; las VPN y redes corporativas pueden usar DNS interno o bloquear consultas externas.
  • Si DNS responde pero TCP falla: revisa qué IP devolvió DNS y qué dirección probó la herramienta. Considera rutas, políticas y disponibilidad del servicio; una sola prueba no distingue entre estas causas.
  • Si TCP funciona: en PowerShell observa TcpTestSucceeded. Ese resultado confirma la conexión TCP al destino probado, pero todavía pueden fallar TLS, un proxy o la aplicación web.
Límite de la prueba: comprobar TCP 443 no verifica HTTP/3, que utiliza QUIC sobre UDP, ni confirma que una página HTTPS cargue correctamente.

4. Comprueba TLS y la respuesta HTTP

Si tienes curl, prueba una petición completa sin omitir la validación del certificado:

# Windows con curl.exe disponible
curl.exe -v --connect-timeout 10 --max-time 20 https://example.com/ -o NUL

# Linux / macOS con curl disponible
curl -v --connect-timeout 10 --max-time 20 https://example.com/ -o /dev/null

Observa el error de conexión, el intercambio TLS y el estado HTTP. Un 403 o un 500 demuestra que hubo una respuesta HTTP, aunque el acceso o la aplicación tengan un problema. No añadas -k para dar por resuelto un error de certificado. El navegador puede usar otro proxy, resolvedor o protocolo, así que compara ambos resultados.

5. Qué anotar

Registra fecha y hora, dispositivos afectados, URL, error del navegador, DNS consultado, IP resuelta y resultado de cada prueba. Anota también si usas VPN o proxy. Comparte solo lo necesario para soporte: elimina cookies, tokens y datos personales de las salidas.

Resumen: alcance → IP y gateway → DNS → TCP 443 → TLS/aplicación. De abajo hacia arriba, como las capas.
